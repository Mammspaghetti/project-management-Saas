TaskFlow — Guide du projet

Un outil de gestion de projets et de tâches multi-utilisateurs : ce document explique comment il est construit, comment fonctionnent Spring Boot et Docker ici, et pourquoi l'architecture est organisée ainsi.

1. Vue d'ensemble

Ce que fait l'application : des utilisateurs s'inscrivent, créent des projets, y invitent d'autres personnes avec un rôle (propriétaire, membre, lecteur) et gèrent des tâches dans un tableau kanban (À faire → En cours → Terminé).

Frontend

React · TypeScript · Vite

L'interface que voit l'utilisateur, dans le navigateur. Elle ne contient aucune donnée : elle appelle l'API.

Backend

Java 21 · Spring Boot

L'API REST : elle applique les règles métier, vérifie qui a le droit de faire quoi, lit et écrit en base.

Base de données

MySQL 8.4 · Flyway

Stocke utilisateurs, projets, membres, tâches. Le schéma est versionné par des scripts SQL.

Docker

Compose

Emballe les trois éléments ci-dessus pour les lancer ensemble avec une seule commande.

3. L'architecture : Clean Architecture

L'idée centrale : le code métier ne doit dépendre de rien de technique (ni Spring, ni la base de données, ni HTTP). C'est la technique qui dépend du métier, jamais l'inverse. Ainsi le métier reste simple, testable seul, et on peut changer de base ou de framework sans le réécrire.

Les 4 couches

CoucheContientExemple dans le code
domainLes objets métier et leurs règles. Java pur, sans annotation de framework. Définit aussi des interfaces (« ports ») que d'autres devront implémenter. Project.addMember() refuse un second propriétaire. TaskRepository est une interface : « sauvegarder une tâche », sans dire comment.
applicationLes cas d'usage : ce que l'application sait faire (créer un projet, assigner une tâche…) et qui a le droit de le faire. TaskService.create() vérifie le rôle via ProjectAccess, puis appelle TaskRepository.save().
infrastructureLes implémentations techniques des interfaces : base de données, hachage de mot de passe, JWT, configuration. TaskRepositoryAdapter implémente TaskRepository avec JPA. JwtTokenIssuer fabrique les tokens.
webL'interface HTTP : reçoit les requêtes JSON, les valide, appelle un cas d'usage, renvoie la réponse. TaskController expose POST /api/v1/projects/{id}/tasks.
Pourquoi des « interfaces » dans le domaine ? Le cas d'usage a besoin de sauvegarder une tâche, mais ne doit pas connaître MySQL. Il appelle donc l'interface TaskRepository (définie dans domain). Au démarrage, Spring branche l'implémentation JPA située dans infrastructure. On parle d'inversion de dépendance. Dans les tests, on peut brancher à la place un faux dépôt en mémoire.

Deux modèles pour la même chose : pourquoi ?

Une tâche existe sous trois formes, volontairement :

  • Task (domain) : l'objet métier, sans framework ;
  • TaskJpaEntity (infrastructure) : la même chose avec les annotations JPA pour la table tasks ;
  • TaskResponse (web) : ce qu'on renvoie en JSON au client.

Cela évite qu'un changement de base ou d'API ne casse le métier, au prix d'un peu de code de conversion.

Parcours d'une requête : créer une tâche

  1. Le navigateur envoie POST /api/v1/projects/1/tasks avec l'en-tête Authorization: Bearer <jwt>.
  2. Spring Security vérifie la signature et l'expiration du token. Sinon : 401.
  3. TaskController (web) valide le JSON (titre non vide, longueur max…). Sinon : 400. Il transforme le token en un Actor (id + rôle global).
  4. TaskService.create() (application) demande à ProjectAccess si l'acteur peut écrire dans ce projet. Non-membre : 404. Lecteur : 403.
  5. Le service crée l'objet Task (domain) puis appelle TaskRepository.save().
  6. TaskRepositoryAdapter (infrastructure) convertit en entité JPA et l'écrit dans MySQL.
  7. La réponse remonte : 201 Created avec la tâche en JSON.

Règle vérifiée automatiquement : ArchUnit

Une règle d'architecture non vérifiée finit toujours par être violée. Le test ArchitectureTest fait échouer le build si quelqu'un, par exemple, importe Spring dans domain ou appelle infrastructure depuis web :

noClasses().that().resideInAPackage("com.taskflow.domain..")
    .should().dependOnClassesThat().resideInAnyPackage(
        "com.taskflow.application..", "com.taskflow.infrastructure..", "com.taskflow.web..",
        "org.springframework..", "jakarta..", "com.fasterxml..");
Compromis assumés @Transactional (Spring) est utilisé dans application pour gérer les transactions : seule exception à la pureté, explicitement autorisée. Les contrôleurs appellent directement les classes de service, sans interface « input port » intermédiaire : c'est un choix de simplicité à cette taille.

4. Spring Boot : comment le backend est fait

Les notions de base

NotionExplication
Spring BootUn framework Java qui démarre une application web complète (serveur Tomcat embarqué inclus) avec très peu de configuration. Le point d'entrée est TaskFlowApplication et son main.
StartersDans pom.xml, des dépendances « tout-en-un » : starter-web (API REST), starter-data-jpa (base de données), starter-security, starter-validation, starter-actuator (santé)…
BeanUn objet créé et géré par Spring. Spring en crée un seul exemplaire et le donne à qui en a besoin.
Injection de dépendancesUne classe déclare dans son constructeur ce dont elle a besoin ; Spring le fournit. Ex. : TaskController(TaskService tasks). On ne fait jamais new TaskService() à la main.
AnnotationsDes étiquettes qui disent à Spring quoi faire : @RestController (cette classe expose des URL), @Configuration + @Bean (fabrique d'objets), @Entity (table SQL), @Transactional (tout ou rien en base)…
MavenL'outil de build. pom.xml liste les dépendances. mvnw est un « wrapper » qui télécharge la bonne version de Maven tout seul.

Le « câblage » : UseCaseConfig

Les classes de application n'ont aucune annotation Spring. C'est UseCaseConfig qui les instancie et leur fournit leurs dépendances :

@Configuration
class UseCaseConfig {
    @Bean
    TaskService taskService(TaskRepository tasks, ProjectAccess access) {
        return new TaskService(tasks, access);   // Spring fournit l'implémentation JPA de TaskRepository
    }
}

Configuration : application.yml

spring.datasource.url: ${DB_URL:jdbc:mysql://localhost:3306/taskflow...}
spring.datasource.username: ${DB_USER:taskflow}
spring.datasource.password: ${DB_PASSWORD:taskflow}
app.security.jwt.secret: ${JWT_SECRET:dev-only-secret...}

La syntaxe ${NOM:valeur} signifie : « utilise la variable d'environnement NOM, sinon cette valeur par défaut ». C'est ainsi que Docker Compose injecte les vrais mots de passe sans qu'ils soient écrits dans le code.

Sécurité et JWT

Un JWT (JSON Web Token) est un jeton signé que le serveur remet après connexion. Il contient l'identifiant de l'utilisateur, son rôle global et une date d'expiration. Le client le renvoie à chaque requête ; le serveur vérifie la signature, sans avoir à consulter une base de sessions : on dit que l'API est sans état (stateless).

  • SecurityConfig déclare quelles URL sont publiques (/auth/login, /auth/register, santé, Swagger) et lesquelles exigent un token.
  • Spring Security valide le JWT grâce au module oauth2-resource-server (bibliothèque Nimbus) : aucune dépendance JWT supplémentaire.
  • Le secret de signature vient de JWT_SECRET (32 caractères minimum, vérifié au démarrage).
  • Le CSRF est désactivé : sans cookie de session, cette protection n'a pas de sens ici.

Données : JPA et Flyway

  • JPA / Hibernate fait le lien entre objets Java et tables SQL. Une classe annotée @Entity correspond à une table.
  • Spring Data génère le code des requêtes à partir d'interfaces : findByEmail(String email) devient automatiquement SELECT … WHERE email = ?.
  • Flyway exécute au démarrage les scripts de db/migration dans l'ordre (V1__…, V2__…) et se souvient de ceux déjà appliqués. Hibernate est en mode validate : il vérifie que les entités correspondent aux tables mais ne les modifie jamais.
Règle d'orNe jamais modifier une migration déjà appliquée : ajouter un nouveau fichier V2__description.sql.
TableRôle
usersComptes : email unique, hash du mot de passe, nom, rôle global
projectsProjets, avec leur propriétaire
project_membersQui appartient à quel projet, avec quel rôle (clé primaire = projet + utilisateur)
tasksTâches : statut, priorité, assigné (optionnel), échéance (optionnelle)

API, validation et erreurs

  • Endpoints sous /api/v1 (le v1 permet de faire évoluer l'API sans casser les anciens clients). Liste complète dans docs/api.md ou en direct sur /swagger-ui.html.
  • Validation : les DTO portent des règles (@NotBlank, @Email, @Size). Une requête invalide est rejetée avant d'atteindre la logique métier.
  • Erreurs : GlobalExceptionHandler transforme les exceptions métier en réponses JSON normalisées (RFC 7807). Exemple : NotFoundException devient 404, ConflictException devient 409.
{ "title": "Bad Request", "status": 400, "detail": "Validation failed",
  "errors": { "email": "must be a well-formed email address" } }

5. Rôles et permissions (RBAC)

RBAC = Role-Based Access Control : on n'accorde pas des droits à chaque personne, mais à des rôles. Il y a deux niveaux :

  • Rôle global : USER (par défaut) ou ADMIN (voit tout, accède à l'espace admin). Il est porté par le JWT.
  • Rôle par projet : OWNER, MEMBER ou VIEWER. Il est lu en base à chaque requête.
ActionVIEWERMEMBEROWNERADMIN
Lire projet, membres, tâches✅✅✅✅
Créer / modifier / supprimer des tâches❌✅✅✅
Modifier ou supprimer le projet, gérer les membres❌❌✅✅
Lister tous les utilisateurs❌❌❌✅
Détail de sécurité : 404 plutôt que 403 Si tu n'es pas membre d'un projet, l'API répond 404 (introuvable) et non 403 (interdit) : on ne révèle pas qu'un projet existe. Tu reçois 403 seulement si tu es membre mais sans droit suffisant.

Les droits sont vérifiés côté serveur, dans ProjectAccess. Le frontend masque certains boutons, mais ce n'est que du confort : la vraie barrière est l'API.

6. Docker : comment ça marche ici

Les concepts

TermeExplication
ImageUn « modèle » figé contenant un programme et tout ce qu'il faut pour tourner (système minimal, Java, tes fichiers…). Se construit à partir d'un Dockerfile.
ConteneurUne image en cours d'exécution : un mini-environnement isolé. Tu peux en lancer plusieurs à partir d'une même image.
DockerfileLa recette pour fabriquer une image, étape par étape.
Docker ComposeUn fichier (docker-compose.yml) qui décrit plusieurs conteneurs et comment ils s'articulent, pour tout lancer d'une commande.
VolumeUn espace de stockage qui survit à la suppression du conteneur. Sans lui, la base MySQL serait vidée à chaque arrêt.
RéseauCompose crée un réseau privé où les conteneurs se joignent par le nom du service (db, backend).
Port"8081:80" signifie : le port 80 du conteneur est accessible sur le port 8081 de ton PC.

Dockerfile du backend (build en 2 étapes)

# Étape 1 : COMPILER (image lourde avec Maven + JDK)
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /workspace
COPY pom.xml .
RUN mvn dependency:go-offline          # télécharge les dépendances (mis en cache)
COPY src ./src
RUN mvn -DskipTests package            # produit target/taskflow-backend-*.jar

# Étape 2 : EXÉCUTER (image légère avec seulement le JRE)
FROM eclipse-temurin:21-jre
RUN useradd --system --uid 1001 app    # utilisateur non-root, par sécurité
COPY --from=build /workspace/target/*.jar app.jar
USER app
ENTRYPOINT ["java", "-jar", "app.jar"]

Pourquoi 2 étapes ? L'image finale ne garde que le .jar et le JRE : elle est bien plus petite et ne contient ni code source ni Maven. Copier pom.xml avant src permet à Docker de réutiliser le cache des dépendances tant que le pom.xml ne change pas : les reconstructions sont plus rapides.

Dockerfile du frontend

FROM node:22-alpine AS build           # étape 1 : compiler React
RUN npm ci && npm run build            #   produit le dossier dist/ (fichiers statiques)

FROM nginx:1.27-alpine                 # étape 2 : servir
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html

Même principe : Node sert à compiler, puis seul le résultat statique est copié dans nginx. nginx.conf fait deux choses : renvoyer index.html pour toutes les pages (nécessaire pour une SPA), et relayer /api/ vers http://backend:8080.

docker-compose.yml

services:
  db:                                  # MySQL
    image: mysql:8.4
    environment: { MYSQL_ROOT_PASSWORD, MYSQL_USER, MYSQL_PASSWORD, ... }   # lus dans .env
    volumes: [ db-data:/var/lib/mysql ]            # données conservées
    healthcheck: ...                               # "db est prête" quand mysqladmin répond

  backend:
    build: ./backend                               # construit via backend/Dockerfile
    depends_on: { db: { condition: service_healthy } }   # attend que MySQL soit prête
    environment:
      DB_URL: jdbc:mysql://db:3306/taskflow...     # "db" = nom du service MySQL
      JWT_SECRET, ADMIN_EMAIL, ...                 # lus dans .env
    ports: ["8080:8080"]

  frontend:
    build: ./frontend
    depends_on: [backend]
    ports: ["8081:80"]
  • Les variables ${...} viennent du fichier .env à la racine. .env est ignoré par Git : c'est là que vivent les secrets.
  • Le healthcheck évite que le backend démarre avant que MySQL soit prête (ce qui le ferait planter).
  • Le backend joint la base avec l'adresse db, pas localhost : dans un conteneur, localhost désigne le conteneur lui-même.

Commandes utiles

CommandeEffet
docker compose up --buildConstruit les images et démarre tout
docker compose up -d dbDémarre seulement MySQL, en arrière-plan
docker compose psÉtat des conteneurs
docker compose logs -f backendSuit les logs du backend
docker compose downArrête et supprime les conteneurs (les données restent)
docker compose down -vIdem et efface la base (repart de zéro)
Piège classique Après une modification du code, il faut --build, sinon Docker réutilise l'ancienne image. De même, MySQL ne lit MYSQL_PASSWORD qu'à la création du volume : si tu changes le mot de passe dans .env après coup, fais docker compose down -v.

7. Frontend React

frontend/src/
├── app/App.tsx                 routes + providers
├── features/
│   ├── auth/                   connexion/inscription, AuthContext, ProtectedRoute
│   ├── projects/               liste des projets, tableau kanban, appels API
│   └── admin/                  page réservée aux admins
└── shared/
    ├── api/http.ts, types.ts   client HTTP et types des DTO
    └── ui/Layout.tsx           barre de navigation
  • Organisation par fonctionnalité : tout ce qui concerne les projets est dans features/projects.
  • http.ts : un petit client qui ajoute le token à chaque requête, transforme les erreurs de l'API en ApiError et déconnecte l'utilisateur si le serveur répond 401 (token expiré).
  • AuthContext : garde l'utilisateur connecté (le token est conservé dans localStorage).
  • ProtectedRoute : redirige vers /login si on n'est pas connecté, et protège les pages admin.
  • TanStack Query : charge les données du serveur, les met en cache et les rafraîchit après chaque modification (ex. ajout d'une tâche).
  • TypeScript : les types dans types.ts reprennent ceux de l'API, ce qui évite de se tromper de nom de champ.

8. Tests et CI/CD

TestCe qu'il vérifieNécessite
ArchitectureTestLes règles de dépendance entre couches—
TaskServiceRbacTestLes droits : lecteur, membre, propriétaire, non-membre, admin—
ProjectDomainTestRègles métier du projet (un seul propriétaire…)—
ApiIntegrationTestL'application entière contre un vrai MySQL : inscription, connexion, droits, validationDocker
Vitest (frontend)Routes protégées, client HTTP—

Testcontainers démarre un MySQL jetable dans Docker pendant le test, puis le supprime : on teste avec le vrai moteur de production plutôt qu'une base simulée.

CI/CD (GitHub Actions) : à chaque push ou pull request, .github/workflows/ci.yml exécute automatiquement :

  1. le backend : mvnw verify (tests unitaires, ArchUnit, intégration) ;
  2. le frontend : lint, tests, build ;
  3. si tout passe, la construction des deux images Docker (sans les publier).

Cela garantit que le code sur main compile et passe les tests. Étape suivante possible : publier les images sur un registre et déployer.

10. Bugs rencontrés au premier lancement

Deux erreurs de démarrage réelles, utiles pour comprendre Spring :

1. « required a bean of type UserJpaRepository that could not be found »

Cause : les interfaces Spring Data étaient déclarées à l'intérieur d'une autre classe. Spring Data ignore par défaut les interfaces imbriquées.

Correction : @EnableJpaRepositories(considerNestedRepositories = true) dans PersistenceConfig.

2. « required a single bean, but 2 were found : corsConfigurationSource / mvcHandlerMappingIntrospector »

Cause : deux beans du même type existaient et Spring ne savait pas lequel injecter dans filterChain.

Correction : ne plus injecter le bean ; .cors(Customizer.withDefaults()) utilise automatiquement celui nommé corsConfigurationSource.

À retenir Ces deux erreurs auraient été détectées par ApiIntegrationTest, qui démarre toute l'application. Ce test était ignoré faute de Docker disponible pour Maven. Lire le bloc APPLICATION FAILED TO START du log, et surtout les lignes Description et Action, donne presque toujours la solution.
